# glove-env-media

## 1.0.0

### Minor Changes

- [#47](https://github.com/porkytheblack/glove/pull/47) [`75f5616`](https://github.com/porkytheblack/glove/commit/75f5616953b8e84c2f4b9c4b4acf66788e331219) Thanks [@porkytheblack](https://github.com/porkytheblack)! - New adapter: `glove-env-media` — video and audio via ffmpeg.

  Video is the format where "paths in, paths out" pays most. A 200 MB file cannot go anywhere near a context window, so every useful operation is necessarily a path transformation plus a cheap summary — `describe()` and `thumbnail()` are what let a model reason about a video it fundamentally cannot look at.

  `describe`, `thumbnail`, `frames`, `clip`, `concat`, `transcode`, `extractAudio`, `slideshow`. Static ffmpeg and ffprobe binaries ship as dependencies, so there is no system requirement; `ffmpegPath`/`ffprobePath` point at a system build instead.

  **ffmpeg runs on the host; the sandbox still spawns nothing.** Every other adapter is a pure library call and "no process spawning" is one of the environment's stated non-goals, so this is stated plainly in the package README rather than left to be discovered. The subprocess is started by the host-side adapter, never by sandboxed code: a script passes two VFS paths and cannot name a program, pass a flag, or observe that a process was involved. Arguments always reach ffmpeg as an argv array through `execFile`, never a shell string — a path containing a semicolon is a filename, and a test pins it.

  Media work is slow, so ffmpeg gets its own budget (two minutes per call) rather than sharing the script timeout. Arguments are validated before ffmpeg starts, so a CRF of 99 or an end before its start fails as a sentence rather than as usage output; when ffmpeg itself fails, only the last lines of its stderr reach the model, since the build banner is a hundred lines of nothing actionable. Staging directories are removed in a `finally`, on the failure path as well as the success one, with a test that counts them.

  Fixtures are generated by ffmpeg's own test sources rather than committed, and every result is verified by probing it independently — a bug in `describe` cannot make a broken transform look correct.

  One consumer-facing hazard handled on the way: `@ffprobe-installer` ships its binary without the execute bit and relies on a postinstall script that pnpm does not always run, leaving an `EACCES` that explains nothing. The adapter chmods it on first use, and if it cannot, says which file and what to do.

- [#131](https://github.com/porkytheblack/glove/pull/131) [`c069246`](https://github.com/porkytheblack/glove/commit/c069246394d5f05bfb39b3efdbd915c87f4e63b5) Thanks [@claude](https://github.com/apps/claude)! - "Resize this animated GIF" gave back a still, and "extract clean 192k MP3 audio" could not be said at all

  **A 30-frame GIF came out with one frame.** `describe` reported `pages: 30` faithfully, and then every transform decoded frame one and wrote it out alone — so the model was told what it was holding and handed something else. `resize`, `convert`, `crop`, `thumbnail`, `composite` and `text` keep the frames now. The part that is easy to get wrong is which format the decision belongs to: libvips holds an animation as one tall strip, so decoding all thirty frames and handing that strip to the PNG encoder does not flatten it — it writes an image thirty times too tall, which is worse than the flattening it was meant to fix. So the decision is made against the **output** format. `.gif`/`.webp` keeps everything; anything else takes frame one, which is what a still format means; `{ animated: false }` flattens deliberately.

  `rotate` is the one verb an animation cannot survive, and it now says so instead of guessing. libvips refuses a quarter turn on a multi-page image outright, and a half turn "succeeds" by flipping the whole strip — which reverses the frame order. Both were measured before deciding. An animation is refused with the reason and with `{ animated: false }` named as the way out.

  **SVG rasterized perfectly and was undiscoverable.** `.svg` appeared in neither `handles` nor the types, so nothing told a model that `convert('/inbox/logo.svg', '/out/logo.png')` works, and there was no way to ask for a resolution. It is claimed now, with `{ scale: 2 }` or `{ density: 300 }` choosing the rasterization — `scale` because the request arrives as "this logo at 2x" and nobody should have to know that means 144 DPI. Writing an SVG is refused rather than mapped to an encoder that does not exist: sharp reads SVG and cannot write it, and quietly putting PNG bytes into a file named `.svg` is a mistake discovered by whatever opens it next.

  **Nothing could put words on a picture.** sharp has no text primitive, and the composite-an-SVG idiom has enough edges — XML escaping, anchoring without being able to measure a string, a halo that eats the glyphs unless `paint-order` is set — that leaving it to callers means it gets written badly, once per caller. `text(input, output, { text, size, colour, outline, gravity, … })` packages it. It defaults to white with a dark halo because a watermark lands on images nobody has looked at, takes multi-line text, and marks every frame of an animation rather than only the first.

  **`extractAudio` was `-vn` and hope.** The container's defaults chose the codec and the bitrate, which is how "extract the audio" answers a request for a 192k MP3 with 64 kbps mono AAC. It takes `codec`, `bitrate`, `sampleRate` and `channels` now — including `codec: 'copy'`, which moves the encoded stream across untouched and losslessly. A bitrate alongside `copy` is refused rather than accepted and ignored, because ffmpeg ignoring it reads exactly like it having worked.

  **`describe` reported subtitle streams and nothing could act on them.** `extractSubtitles` writes a track out (and converts on the way — `.srt` in, `.vtt` out), `burnSubtitles` paints it into the picture from either an embedded track or a subtitle file in the tree. `describe` now carries `track`, `language` and `title` per stream, where `track` counts within a kind — a model asking for "the second subtitle" should not have to subtract the video and audio streams first, and it is the same number both verbs take. A track that is not there is checked before ffmpeg starts, because the alternative arrives as `Stream map '0:s:0' matches no streams` or as filter-graph noise whose one useful line has already been trimmed off the end of stderr.

  **Nothing measured loudness.** `loudness(path)` reports integrated LUFS, true peak, range and threshold — the units a platform spec is actually written in. `normalize` hits a target in two passes, always: loudnorm run blind is a dynamic compressor that lands _near_ a target, and the difference between "near −14 LUFS" and "−14 LUFS" is the entire reason anyone asks. Video streams are copied rather than re-encoded. `waveform` is to audio what `thumbnail` is to video — a model cannot listen any more than it can look, and dead air, clipping and "is there anything in here" are one glance in a picture.

  One thing worth stating because it constrained the design: **a filename inside an ffmpeg filter graph is parsed, not passed through** — `:` starts the next option and `\` escapes — so there is no general safe escaping for a caller's path there. `burnSubtitles` runs ffmpeg from inside the staging directory and names a bare file already reduced to `[\w.-]`, and every colour and size that reaches a graph is pattern-checked first. `ffmpeg()` also returns its stderr now, since the measuring filters print their numbers there and nowhere else.

  32 tests added across the two packages — 41/41 images, 31/31 media — all asserting on the artifact rather than on the call: a four-frame GIF whose frames carry distinguishable colours, so both the count _and_ the order are checked through every verb; extracted audio probed by ffprobe for the codec, sample rate and channel count that were asked for; a −30 dB tone measured back at −14 LUFS after normalization; a burned-in caption compared against the same frame of a plain transcode, so "ffmpeg produced a file" cannot pass for "the subtitle is visible".

### Patch Changes

- [#131](https://github.com/porkytheblack/glove/pull/131) [`416d1dd`](https://github.com/porkytheblack/glove/commit/416d1ddb992e6b82119f9eef78c8af7dfe96014e) Thanks [@claude](https://github.com/apps/claude)! - Adapters accept a range of hub versions instead of pinning one exactly

  Every `glove-env-*` declared its `glove-working-environment` peer as `workspace:*`, which pnpm rewrites to an **exact** version at publish time. The published packages had already diverged because of it — `glove-env-documents@0.1.0` required exactly `0.1.0` while `glove-env-motion@0.1.0` required exactly `0.2.0`, so installing both from npm was unsatisfiable, and every future hub release orphaned every adapter already out there.

  The peer is now `workspace:^`, which publishes as a caret range (`^0.2.0`). Verified against a real `pnpm pack` tarball rather than assumed from the source manifest.
